# Reproducibility Guide

Quantum Compass separates reproducible simulation code from evidence generated by a real quantum service. This guide explains what can be reconstructed from the repository, what must be retained from a particular hardware run, and how to avoid turning a recovery or replication into an undocumented duplicate experiment.

## Reproducibility levels

| Level | What can be reproduced | Required record |
|---|---|---|
| Source and unit tests | App behavior, manifest validation, count normalization, and deterministic simulator tests | commit hash or release archive, Python dependencies |
| Deterministic simulator study | A named ideal/noise-model landscape under fixed inputs | source revision, inputs, seed, exported data |
| Hardware analysis | The calculations applied to a saved count dataset | manifest, raw/normalized counts, analysis export, source revision |
| Hardware execution | A new measurement under a related protocol, not the same historical physical event | all of the above plus a new job ID, timestamp, backend state, and explicit replication label |

A completed QPU job cannot be replayed exactly: device calibration, queue delay, compilation, scheduling, and stochastic sampling can differ. The appropriate goal is transparent reconstruction of the original analysis and clearly labelled replication, not numerical identity across hardware executions.

## Reconstructing the software environment

Use the supported interpreter from `runtime.txt` and the repository requirements:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pytest tests/test_core.py -q
python -m compileall -q app.py core utils pages scripts tests
```

The Docker image is an additional reproducible execution route. From the repository root:

```bash
docker compose build
docker compose run --rm --no-deps quantum-compass python -m pytest tests/test_core.py -q
docker compose run --rm --no-deps quantum-compass python -m compileall -q app.py core utils pages scripts tests
```

The project does not claim that a generic package range alone recreates an old physical execution. Capture a local package record with the study evidence when it is complete.

## Capture study-local provenance honestly

Run the following from the real checkout and environment used to produce or analyse the study. It creates a package/runtime record and SHA-256 listing from actual local files; it does not create fake data, backdate anything, or include credentials.

```bash
python scripts/capture_study_provenance.py --study-dir studies/descriptive-study-name
```

For a containerized analysis using the bind-mounted `studies/` directory:

```bash
docker compose run --rm --no-deps quantum-compass python scripts/capture_study_provenance.py --study-dir studies/descriptive-study-name
```

This writes:

- `environment.json` — Python implementation/version, OS family details, installed distribution versions, and explicit non-storage flags for credentials and host identity; and
- `SHA256SUMS.txt` — SHA-256 hashes for the study files, including `environment.json` but not the checksum file itself.

Use `--overwrite` only when intentionally recapturing these generated records from the correct study environment. Never fabricate or copy them from an unrelated machine.

## Recover an interrupted Runtime workflow

For a new submission, the CLI creates `submission_receipt.json` immediately after IBM Runtime returns the job ID. If a terminal, network session, or container exits while the QPU job is queued or running, do not submit again. Restore the same environment variable and recover the original job:

```bash
python scripts/submit_ibm_validation.py \
  --manifest studies/descriptive-study-name/qaoa_validation_manifest.json \
  --backend your_backend_name \
  --job-id recorded_runtime_job_id \
  --output-dir studies/descriptive-study-name/backend_run
```

The recovery path obtains `service.job(job_id)`, retrieves its result, writes `job_recovery_receipt.json`, and marks `run_metadata.json` with `result_source: recovered_existing_job`. It neither changes the manifest nor sends another circuit batch.

## Reproduce the analysis

1. Verify the manifest ID and checksum before uploading any counts.
2. Keep raw Qiskit keys in `raw_qiskit_counts.json` and use the CLI-produced vertex-order `counts_long.csv` in the app.
3. Upload the original manifest and complete count CSV to page **🧪 Experimental Validation**.
4. Export the analysis JSON, Markdown report, and any visual used in public communication.
5. State the backend, job ID, condition count, shots, compiler configuration, and evidence limitations when reporting results.

The app's analysis can be rerun from preserved raw evidence. It must not be used to replace raw data, omit unfavorable conditions, or change a preregistered endpoint after inspecting hardware outcomes.

## Evidence boundary for the completed IBM study

The repository's documented `ibm_kingston` pilot/final workflow is a completed, fixed historical study. Its final six-qubit result is limited to the preregistered manifest, backend, execution period, compiler configuration, and observed count data recorded in [`docs/research/hardware_validation_results.md`](docs/research/hardware_validation_results.md). It supports simulator-agreement analysis only; it does not establish quantum advantage, a universal device model, or physical-noise attribution.
